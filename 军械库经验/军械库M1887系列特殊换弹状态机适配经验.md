# 军械库 M1887 系列特殊换弹状态机适配经验

## 使用前提与结论

本经验来自 m1887、m1887_hc 的 Java 动画与网易版换弹适配，可与《军械库特殊换弹specialReload配置与动画适配经验》配合阅读。

最重要的结论：特殊动画不等于需要一套新的换弹系统。优先复用项目已稳定运行的换弹入口、倒计时、背包取弹、扣弹和保存流程。smle_mk3 是本次选取的现有范例。

最终路线：

```text
TestItemInBag / GetSpecialReloadMini
    -> StartReload
    -> GetSpecialReload / Special_A
    -> reloadTick 原生倒计时
    -> ReloadBullet 到点装入
    -> TestItemInBag 决定继续或结束
    -> ReloadLoop / EndReload
```

专用模块只负责选择动作、生成本轮参数、维护膛内状态及通知动画控制器。不要重新建立独立换弹计时器、专用扣弹协议或另一套库存一致性检查。

## 最终职责划分

| 层级 | 职责 |
|---|---|
| 枪包配置 | 声明 specialReload、动画短名、摄像机和特殊收尾装弹时点 |
| 原生换弹代码 | 准备弹药、倒计时、到点装入、背包扣弹、同步、判断继续装填 |
| m1887GunState 适配模块 | 选择普通循环或特殊收尾，把特殊动画拆为原生计时段，维护膛内状态 |
| 枪包专用控制器 | 播放起手、交替循环、特殊收尾、中断、两种拉栓等状态 |
| 摄像机系统 | 复用现有播放接口，同一特殊动作只启动一次镜头 |

本次使用已有 M1887 专用控制器，不再新增一套 overlay 控制器。其它武器只有在显式启用对应 profile 或控制器时才进入适配分支。

## 原生逐发换弹配置

- `reloadType: 1` 启用逐发路线。
- `specialReload.type: "a"` 复用现有特殊换弹数据选择。
- 每个装填时点的准备数量保持 1。特殊动画中有两次装填，不等于一次提交两发。
- 普通起手约 1.8 秒，循环动画约 1.4167 秒，循环开始后约 0.8 秒装入一发。
- 起手只播放开枪机动作，不在起手阶段装弹。本项目已有配置可将起手装弹时间设在起手结束之后，使该倒计时事件不触发；必须核对实际换算结果。

`Special_A` 内的时间字段以秒配置，内部换算为原生倒计时：

```text
阶段 tick = int(阶段秒数 * 30 / ep_use_speed)
装弹倒计时 tick = int((阶段秒数 - 装弹时点秒数) * 30 / ep_use_speed)
```

计数递减到装弹 tick 时，调用原有 ReloadBullet。不要在专用模块中再次乘 30 或除以速度。

注意：以上装弹时点语义指 Special_A 内的数据。直接配置普通 reloadLoopBullet 的路径可能已有不同的转换方式，不能只凭字段同名认定两者完全相同。

默认速度下，1.4167 秒会被当前原生转换截为 42 tick，实际每轮约 1.4 秒。这是原系统的 tick 精度，不应再用另一套墙上时钟补偿。

## Java 特殊收尾的接入方式

本次配置增加可选 `m1887ReloadEndings`：

```json
"m1887ReloadEndings": {
    "reload_end_1round": {
        "feedTimes": [0.6],
        "logicDuration": 1.75
    },
    "reload_end_2round": {
        "feedTimes": [0.6, 2.1],
        "logicDuration": 3.1
    },
    "reload_end_empty": {
        "feedTimes": [0.6, 2.1, 2.6],
        "logicDuration": 3.75
    }
}
```

这些数值是本次 M1887 适配采用的参数，不是其它枪械的通用默认值。

- `feedTimes`：从整段特殊动画开始计算的各次装弹时点，单位秒。
- `logicDuration`：整段动作的逻辑结束时间，单位秒。
- `m1887Actions`：保存动作短名对应的视觉持续时间和摄像机名称。
- `stateProfile: "tacz_m1887"`：逻辑适配入口。
- `stateController`：沿用项目已有的枪包控制器覆盖入口。

选择规则：

| 条件 | 动作 |
|---|---|
| 非空仓开始换弹，剩余容量大于 2 | 普通逐发循环 |
| 非空仓开始换弹，只缺 1 发 | reload_end_1round |
| 非空仓开始换弹，只缺 2 发 | reload_end_2round |
| 空仓开始换弹，逐发装到剩余 3 个总弹位 | reload_end_empty |
| 主动中断或备弹不足 | reload_int / reload_int_empty |

空仓剩余 3 个弹位包含本次 6+1 总弹量模型的需求，不能原样套用到没有独立膛内语义的武器。

### 一段动画，多次原生装填

特殊动画保持连续播放，内部装弹事件拆成几轮原生倒计时。以补两发为例：

```text
整段逻辑时长 3.1 秒，装弹时点 0.6 / 2.1 秒

第一计时段：长度 0.6 秒，到结束时装入第 1 发
第二计时段：长度 2.5 秒，段内 1.5 秒时装入第 2 发
第二段结束后，整段逻辑完成
```

每段仍由 Special_A 生成参数，使用 ReloadLoop、ReloadBullet 和原来的背包处理。每次只准备、扣除、装入一发。

后续计时段必须保持同一动画状态，并跳过摄像机重播。否则每装一发就从头播放特殊收尾，会导致动作卡住或镜头跳动。

完整特殊收尾已包含关栓：自然完成时，不再追加 reload_int，也不再叠加一段 reloadEndTick。中途取消则使用对应中断动作，只保留已经实际装入的子弹。

## 逻辑结束与视觉结束

本任务确认采用 Java 逻辑时序：逻辑结束后允许操作，动画保持原速；没有新操作时，视觉尾段继续播完。

- logicDuration 与 animation_length 可以不同。
- 不要为了让两者相等而拉伸或减慢动画。
- 新射击可以中断已经逻辑解锁的视觉尾段。
- 自然结束特殊收尾与中途中断必须分开判断。
- 普通循环结束后使用纯关栓动作；已经完整播放特殊收尾时不重复关栓。

## 动画资源与控制器经验

### 不要统一叠加 static_idle

部分网易版动画已经包含完整持枪姿态，再叠 static_idle 会造成位移、旋转或手臂缩放重复。

必须逐段检查动画是完整姿态还是相对偏移动作。Java 有独立基础轨道，不代表转换后的 Bedrock 动画也必须再叠加基础轨道。

本次用户手动去除了大部分状态中的 static_idle，这些调整需要保留。不能把其它枪械或 last_shoot 的经验直接推广成“所有状态都要带 static_idle”。

### 首尾平滑帧可能导致 HC 飞手

用户在游戏中确认，m1887_hc 飞手与首尾关键帧采用平滑帧有关。

- 优先检查手臂位置、旋转通道的首尾关键帧及 Catmull-Rom 插值。
- 首尾使用明确、稳定的姿态，避免端点平滑插值产生异常。
- 不要仅通过补 idle、放大过渡时间或降低动画速度掩盖该问题。
- 这是本案例确认的原因，不代表所有飞手问题都来自平滑帧。

### 摄像机停在最后一帧

本项目这些动作摄像机必须配置：

```json
"loop": "hold_on_last_frame"
```

不要写成 true，那会循环播放。缺少末帧保持时，本项目摄像机结束处理可能还原旧视角，造成异常跳动。

特殊收尾分段推进时，镜头仅在第一段启动。切枪、死亡或新动作开始时，仍要按现有流程停止旧镜头。

### 循环与拉栓

- 普通循环使用 A/B 两个状态交替，配合可以重新播放的动画绑定。
- 主动作由已注册短名引用，不在控制器内用完整 animation 名称绕过绑定。
- 含无限 idle 的状态不要依赖 all_animations_finished 判断装填完成。
- HC 普通拉栓与翻转拉栓按 60% / 40% 选择，每次动作只随机一次。
- 两种 HC 拉栓配合 bolt_charge，摄像机与动作一致。
- 翻转动作要检查轴心。本次使用专用翻转骨骼承接动作，保留原模型其它骨骼关系。

## 弹药与膛内状态

本次采用 6 发弹管加 1 发膛内：

- nowBullet 表示总弹量，满载为 7。
- m1887_chambered 记录膛内是否有弹。
- 弹管数量由总弹量减去膛内数量得到。
- 旧物品缺少字段时，有弹视为已上膛，但不额外增加子弹。
- 拉栓上膛只改变弹药位置，不增加总弹量。
- 切枪和硬中断保留已完成的装填结果，不继续旧换弹计时。

最终实现通过原有 ReloadBullet 保存弹量并附带膛内字段，通过现有物品状态链保存上膛结果。不要重新启用被撤除的专用单发提交协议。

## 本次走过的错误路线

1. 独立换弹调度器与原生换弹流程同时存在，增加了状态、中断和同步冲突点。即使独立模块测试通过，也不代表游戏实际入口正确。
2. 使用墙上时钟加 while 追赶装弹事件，可能在一次更新中补执行多发，跳过可见循环。最终通过回归原生 tick 计时解决架构问题，而不是继续维护该调度器。
3. 专用服务端校验要求新弹量严格等于库存旧弹量加一，遇到不同步快照时可能拒绝正常装填；拒绝回调再写回旧满弹数，会呈现“装一发后瞬间满弹并结束”。曾用模拟测试复现这条路径，但未单凭客户端日志证明每次游戏异常都来自它。
4. 为此继续增加装填会话、序号、回执和专用纠正逻辑，复杂度上升，用户仍反馈问题。最终这些专用机制被移除，统一使用其它枪械已工作的原生协议。
5. 对所有状态机械添加 static_idle，忽视转换后的动画已包含基础姿态，造成叠加错位。

后续维护应以最终原生路线为准，不要把中间尝试恢复为推荐实现。

## 排查与验收

排查时先区分三种现象：子弹数字没有增加、数字增加但动画没循环、数字被突然改成满弹。三者不能仅靠调整动画时间解决。

建议检查：

- 合并默认值、配件和 selectData 后的有效 nowData，而不是只看根配置。
- 初始剩余弹量，以及本次实际需要装入的数量。
- 当前动作、reloadTick、reloadBulletTick、setReloadOverBullet。
- 子弹是在原生 ReloadBullet 中增加，还是被同步回调覆盖。
- 自然结束、备弹耗尽、玩家取消是否走了正确分支。

测试必须实际调用生产代码的 StartReload、ReloadLoop、Special_A、ReloadBullet、EndReload 和 Update 中的倒计时段。只测试自建模拟调度器会遗漏接入问题。

验收至少包含：

- 空仓逐发装满，非空仓缺 1 发、2 发和多发。
- 特殊收尾内每个装弹时点都只增加一发，动画和镜头不重播。
- 第一发装入前后中断，第二发准备期间停止，切枪或死亡。
- 特殊收尾中备弹不足：只保留已装数量，并播放中断动作。
- 速度倍率变化后原生 tick 仍能命中装弹时点。
- 服务端库存仍留有旧弹量时，沿用原生结算，不执行专用满弹回写。
- smle_mk3 等未启用 M1887 配置的枪械继续使用原分支。
