# 军械库移动姿态与弹药箱动画适配经验

更新时间：2026-09-14

适用范围：网易 ModSDK / Minecraft 中国版军械库前置与附属枪械、近战、道具资源包。

## 核心结论

动画移动层的阻塞条件，必须使用“当前动作是否仍占用移动表现”的状态，不能直接使用仍在倒计时的战斗窗口变量。

本次验证得到两条稳定规则：

1. 格挡松手后，`parryTick` 仍可能继续倒计时，但格挡动画已经结束；移动动画应立即恢复。
2. 弹药箱等道具如果同时注册旧 `ep_walk_co` 和新的加权移动控制器，会出现移动动画重复、姿势覆盖或战术冲刺异常。

## 一、格挡结束后奔跑动画消失

### 问题链路

```text
开始格挡
  -> rightClick = True
  -> epMelee.isParry = True
  -> parryTick = 完美格挡窗口
  -> 移动表现被暂停

松开格挡
  -> rightClick = False
  -> epMelee.EndParry()
  -> 格挡动画结束
  -> parryTick 仍大于 0
```

如果移动状态机把 `parryTick > 0` 视为“仍在格挡”，松手后的恢复请求会继续被拒绝。等 `parryTick` 自然归零后，如果没有新的移动事件，动画就会停在 0；战术冲刺则可能落进走路兜底。

### 正确判定

格挡动画是否阻塞移动层，应使用实际输入/动作状态：

```python
if nowType == 1 and rightClick:
    return True
```

不要用 `parryTick` 判断移动动画是否继续阻塞。`parryTick` 只负责完美格挡判定窗口和其它战斗逻辑需要的时间窗口，不代表格挡按键仍被按住。

### 代码层建议

在统一的移动表现裁决入口中处理：

```python
def _Test_Has__Run(self):
    ui = self.epGunUi
    if getattr(ui, 'nowType', None) == 1 and getattr(ui, 'rightClick', False):
        return True
    # 其它真实仍在进行的动作继续阻塞移动表现
    ...
```

战术冲刺的视觉阻塞判断也使用相同规则，不要单独保留 `parryTick` 分支，否则普通奔跑恢复了，战术冲刺仍可能被挡住。

### 重要边界

- 不要在松开格挡时强制 `parryTick = 0`，这会改变完美格挡窗口。
- 不要增加每 tick 检查 `parryTick` 是否归零来补动画；这属于用轮询掩盖状态定义错误。
- 松开格挡后应由现有 `_FinishActionMovePresentation()` / `RefreshMovePresentation()` 立即重新裁决。
- 道具使用也可能复用 `parryTick` 作为冷却变量，因此更不能全局粗暴清理。

## 二、弹药箱移动动画适配

前置弹药箱配置通常位于：

```text
<项目根目录>/resource_pack_EP_JXK_0/modconfigs/EP_JG_DATA/
```

动画资源通常位于：

```text
<项目根目录>/resource_pack_EP_JXK_0/animations/
```

本次前置中的弹药箱配置为：

```text
i_bullet_box_iron.json
i_bullet_box_gold.json
i_bullet_box_diamond.json
```

### 控制器注册规则

当前加权移动体系使用：

```json
["ep_co", "controller.animation.ep_zg.melee_weight_co"]
```

弹药箱配置中不要再同时保留：

```json
["ep_co", "controller.animation.ep_zg.ep_item_co"]
["ep_walk_co", "controller.animation.ep_zg.walk"]
```

否则同一个物品会有两套移动表现同时参与：一套由旧控制器控制，另一套由 Python 权重系统控制，跑步、滑铲、趴下或战术冲刺时可能互相覆盖。

迁移后应只保留一个 `ep_co` 移动控制器和必要的跳跃控制器：

```json
"AnimationController": [
    ["ep_state", "controller.animation.ep_zg.ep_item_state_use"],
    ["ep_co", "controller.animation.ep_zg.melee_weight_co"],
    ["ep_jump_co", "controller.animation.ep_zg.jump_co"]
]
```

### 起跑/收跑时间轴

如果弹药箱的 `run_start` 和 `run_end` 由加权移动系统按代码时间驱动，动画文件需要保留真实长度，并使用对应 Molang 时间轴：

```json
"animation.bullet_box.run_start": {
    "loop": "hold_on_last_frame",
    "animation_length": 0.5333,
    "anim_time_update": "query.mod.ep_time_run_start"
}
```

```json
"animation.bullet_box.run_end": {
    "loop": "hold_on_last_frame",
    "animation_length": 0.8833,
    "anim_time_update": "query.mod.ep_time_run_end"
}
```

`animation_length` 必须与实际动画资源一致。不要为了让动画“看起来能播”随意填 1.0；时间不一致会导致起跑或收跑还未结束就进入下一状态。

### `first_guiwei` 兼容项

如果道具使用逻辑会注册 `first_guiwei`，配置中要同时声明该短名：

```json
["guiwei", "animation.iso_hemlock.guiwei"],
["first_guiwei", "animation.iso_hemlock.guiwei"]
```

缺少短名时，某些切换或重建渲染路径可能出现动画找不到或归位不一致。

## 三、排查顺序

1. 配置的 `type` 是否为近战或道具类型。
2. `render.AnimationController` 中是否有重复的移动控制器。
3. 是否仍注册了 `ep_walk_co`，以及前置代码是否又额外注册了一次。
4. `ep_co` 是否指向当前项目使用的移动控制器。
5. `render.Animations` 是否包含 `ep_run_start`、`ep_run`、`ep_run_end`。
6. 一次性起跑/收跑动画是否使用了正确的 `ep_time_run_start/end`。
7. 移动状态阻塞条件是否误用了 `parryTick`、冷却或其它延迟归零变量。
8. 战术冲刺是否仍绑定了对应的 `ep_tactical_sprint` 动画。

推荐使用文本检索而不是盲目整文件回退：

```powershell
rg -n "ep_walk_co|melee_weight_co|ep_run_start|ep_run_end|ep_tactical_sprint|parryTick" <项目根目录>
```

## 四、修改原则

- 移动控制器一次只启用一套。
- 枪械、近战、道具的控制器策略要按项目现有体系判断，不要把道具误当枪械处理。
- `parryTick` 只负责时间窗口，不负责判断格挡动画是否仍在播放。
- 优先修统一状态裁决入口，不在每个按钮回调中增加互相调用。
- 不用每 tick 扫描补救由错误状态条件造成的动画卡住。
- 资源迁移时只修改控制器注册和必要的时间轴字段，不要无关回退攻击、检视、格挡、使用动作。
- 所有 Python 代码保持 Python 2.7 兼容。

## 五、验证清单

### 格挡与移动

- 奔跑时按下格挡再立即松开，普通奔跑动画恢复。
- 战术冲刺时按下格挡再立即松开，战术冲刺姿势和摄像机恢复。
- `parryTick` 未归零时，完美格挡窗口仍然有效。
- 道具使用冷却不受影响。

### 弹药箱

- 铁、金、钻石弹药箱都只注册一套移动控制器。
- 普通走路、起跑、循环跑步、收跑都正常。
- 趴下、滑铲、战术冲刺不会出现双重姿势或手臂飞动。
- `first_guiwei`、使用、检视、打开/关闭动作不受影响。

## 给后续 AI 的简短提示

遇到“松手后移动动画不恢复”，先问：这个变量代表按键持续状态，还是只代表一个仍在倒计时的判定窗口？

遇到“道具跑步姿势异常”，先问：是不是旧 `ep_walk_co` 与现代权重移动控制器同时注册？

这两问通常比继续增加条件或 tick 轮询更快找到根因。
